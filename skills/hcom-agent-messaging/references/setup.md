# What hcom installs and loads

Installing hcom, connecting an agent, and making this optional skill available
are separate operations. By default, a connected agent gets startup
instructions even when no `hcom-agent-messaging` skill is installed.

| Component | Purpose | How it arrives |
|-----------|---------|----------------|
| `hcom` executable | Commands, database access, bundled integration code | Binary/package installation; this checkout's distribution configuration does not install client skill folders |
| Runtime hooks or delivery plugin | Record activity and deliver messages | Prepared by `hcom <tool>`; some tools use session flags, others persistent tool configuration |
| Startup instructions (bootstrap) | Teach a participating agent its identity and hcom commands | Generated by hcom and injected through launch arguments or integration callbacks |
| Optional messaging skill | Additional setup, troubleshooting, and workflow guidance | A client discovers the complete `skills/hcom-agent-messaging/` folder, or a skill plugin exposes it |

`hcom hooks add` does not install this skill. It also does not write the full
bootstrap into `AGENTS.md` or `CLAUDE.md`. This checkout has no `hcom skills
install` command. Installing the skill does not install or update the hcom
executable.

## Runtime setup by tool

| Tool | What `hcom <tool>` prepares | Persistent hook setup |
|------|-----------------------------|-----------------------|
| Claude Code | Merged session `--settings`; the default native delivery mode also loads a bundled delivery mod with `--plugin-dir` | None required for ordinary hcom launches |
| Codex | Session `-c` hook declarations and trust entries; startup instructions through `developer_instructions` | None required for ordinary hcom launches |
| OpenCode, Kilo, Pi, OMP, Copilot, Qoder | Tool-specific per-launch integration flags/environment and generated artifacts | None required for ordinary hcom launches |
| Gemini, Antigravity (`agy`), Cursor (`cursor-agent`), Kimi | Checks and installs missing persistent integration in the tool's configuration | `hcom hooks add <tool>` is the explicit repair/setup path; restart as instructed |
| Hermes | Installs/enables its plugin in the selected Hermes profile | `hcom hooks add hermes` targets the ambient profile; follow its activation output |
| Grok | Native tool connection for status and messaging | No hooks to install |
| Other tools | `hcom start` connects manual participation | Use `hcom listen` for manual delivery |

For per-launch tools, `hcom hooks status <tool>` reports `per-run`; that is an
integration mode, not evidence that a particular running session is connected.
`hcom hooks add claude` and `hcom hooks add codex` report that there is nothing
to install. Per-launch preparation can still clean up old hcom-owned hooks
and synchronize permission-only files; it does not copy the optional skill.

Bare `hcom hooks add` selects the detected current tool, or all tools outside
a recognized tool. `hcom hooks add all` skips per-launch tools and Hermes.
Use `hcom hooks add hermes` explicitly for the ambient profile, or let
`hcom hermes` prepare its selected launch profile.

Claude and Codex also have a separate, opt-in native-session path:
`hcom hooks native add|remove|status <claude|codex>`. Unlike the ordinary
per-launch setup, `native add` installs persistent hooks into the tool's
profile for native participation. It is not needed for `hcom <tool>` launches.
Check native hook status separately; the ordinary `per-run` status label does
not report whether this opt-in configuration is installed.

## Optional skill in Codex

Current [OpenAI skill documentation](https://learn.chatgpt.com/docs/build-skills#where-to-save-skills)
uses `~/.agents/skills/` for personal skills and `.agents/skills/` within a
repository for shared skills. Codex follows symlinked skill folders too.
It initially lists skill metadata and reads the full instructions when the
skill is selected, explicitly or by relevance.

First inspect `/skills` for an existing `hcom-agent-messaging` installation.
A client may already expose a working copy under `~/.codex/skills/` or
`$CODEX_HOME/skills/`; update its reported path instead of adding another copy
with the same name. A plain `skills/` directory at a repository's root is the
distribution source, not the documented repository discovery location.

To install or refresh a personal copy from this checkout, run from its root
and set `skill_target` to the existing path, or the documented default for a
new installation:

```bash
skill_target="$HOME/.agents/skills/hcom-agent-messaging"
mkdir -p "$skill_target"
cp -R skills/hcom-agent-messaging/. "$skill_target/"
```

Copy the entire folder, including `references/` and the example helper.
Copies need refreshing when the source changes. A symlink to the full source
folder is another option when that checkout will remain available. If the
skill does not appear after a change, restart Codex and check `/skills` again.

The copy command adds/overwrites source files; it does not delete obsolete
files from an older copy. For a clean refresh, compare the chosen target with
the source and remove obsolete files or replace that skill folder after
preserving any local edits. For repository scope instead of a personal copy,
`.agents/skills/hcom-agent-messaging` can link to
`../../skills/hcom-agent-messaging`. Keep `skills/` as the distribution source;
choose one discovery scope to avoid duplicate same-named installations.

## Optional skill in Claude Code

Claude Code discovers standalone skills under `~/.claude/skills/` for a user
or `.claude/skills/` for a project. Use the configuration root of the actual
Claude profile when a profile override is active. See
[Claude's skill locations](https://code.claude.com/docs/en/slash-commands#choose-where-skills-load).

For a personal standalone copy, run from this checkout's root:

```bash
skill_target="$HOME/.claude/skills/hcom-agent-messaging"
mkdir -p "$skill_target"
cp -R skills/hcom-agent-messaging/. "$skill_target/"
```

Start a fresh session and look for `/hcom-agent-messaging`. This plain skill
folder can coexist with hcom's automatically loaded delivery mod.

There are two different plugin packages in this repository:

- `src/claude_mod/` is embedded in the executable. The launcher publishes it
  under `<HCOM_DIR>/integrations/claude-mod/` and loads it for native delivery.
  It contains the delivery hook/JavaScript, with no messaging skill.
- `plugin/hcom/` is the optional skill distribution listed by
  `.claude-plugin/marketplace.json`. Its `skills` link points to the repository's
  top-level `skills/` directory. It does not install hcom's runtime hooks.

Both manifests currently use the name `hcom`. Claude's documented
[name-conflict rules](https://code.claude.com/docs/en/plugins/loading#name-conflicts)
give a session `--plugin-dir` copy precedence over an installed plugin with
the same manifest name. Combined with these manifests, this implies that the
default native-delivery launch can shadow the optional marketplace skill
plugin. Use the standalone skill folder above for `hcom claude`.

For marketplace packaging, keep the full repository: Claude can materialize
the shared `skills` symlink when its target stays within that marketplace.
Copying only `plugin/hcom/` can leave the link unresolved. See
[marketplace symlink rules](https://code.claude.com/docs/en/plugins/host-marketplace#share-files-within-a-marketplace-with-symlinks).
The local validator can warn that it skipped the linked directory; validate
the real skill content as well. A plugin installation record alone does not
prove its skill loaded in the running session.

## State roots, updates, and removal

`HCOM_DIR` chooses hcom's database, logs, and generated integration artifacts.
It does not change a tool's own configuration root or move persistent hooks
into the project. Tool profile overrides such as `CLAUDE_CONFIG_DIR`,
`CODEX_HOME`, and `HERMES_HOME` are separate. Local hcom participants need the
same `HCOM_DIR` to use the same database.

An executable update changes its bundled runtime integration/bootstrap code.
A standalone skill copy and a marketplace skill package have their own
update paths. `hcom hooks remove` removes hcom hooks and owned legacy installs,
not standalone skill folders or marketplace installation records. A reset
can stop agents and archive/clear hcom state; it is not a skill installer or
an ordinary discovery repair.

## Check each layer

```bash
command -v hcom
hcom --version
hcom hooks status claude
hcom hooks status codex
hcom hooks native status claude
hcom hooks native status codex
hcom list
hcom config bootstrap show
hcom config bootstrap render example codex launched
```

Use `hcom list <actual-name>` to inspect a particular session's bindings.
Check optional skills in the client's skill selector. In Claude,
`claude plugin list --json` inspects marketplace records; a runtime mod loaded
through launch flags is session-scoped and does not require such a record.
Run these checks for the same profile/state root as the affected session.
The presence of a skill folder does not identify its original installer.
